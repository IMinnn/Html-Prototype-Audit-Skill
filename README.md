# HTML Prototype Audit Skill

面向 B 端 HTML 高保真原型的检查技能。通过实际打开页面、点击控件和走通业务流程，检查功能、交互、视觉及需求覆盖，输出可以直接交给 AI 修改的问题清单。

检查对象是“高保真设计 + 可交互原型”。允许使用静态数据、内存状态和 localStorage 模拟操作，不以真实后台、数据库或生产鉴权作为验收要求。

## 检查什么

| 检查方向 | 主要内容 |
| --- | --- |
| 页面与导航 | 菜单、页签、详情、弹窗、抽屉、返回路径、条件入口是否可达且一致 |
| 功能与业务闭环 | 适用的增删改查、批量操作、状态流转、跨页面联动及结果反馈 |
| 表单与异常状态 | 必填、格式、边界、取消、重置、重复提交、空态、错误与恢复路径 |
| 列表 | 搜索、组合筛选、排序、分页、页容量、总数、选择范围及删除后的页码处理 |
| 文件 | 上传、移除、替换、预览、下载、模板、导入和导出的实际结果 |
| UI 与操作效率 | 简约清晰的信息层级、页面风格一致、布局溢出、遮挡、桌面尺寸适配及基础键盘操作 |
| 界面文案 | 检查并记录“仅前端演示”“当前是 Demo”“暂未接入后台”等演示性质说明 |
| 需求覆盖 | 提供 PRD、背景或流程资料时，逐项映射需求、页面入口和验证场景 |

检查规则按实际业务适用：只读日志不强求编辑和删除，固定少量展示不机械要求分页，未声明移动端支持时不追加移动端验收。

## 演示性质文案检查

用户可见界面不应出现解释当前产品处于演示、模拟或未实现状态的说明，例如：

- “当前是演示 Demo”“仅前端演示”“仅展示效果”。
- “模拟数据”“假数据”“静态演示”。
- “暂时不接数据”“未接入后台”“尚未对接接口”“实际功能待开发”。

检查范围包含页面常驻文字，以及点击后出现的弹窗、悬浮提示、Toast、alert、上传下载反馈等内容。发现后作为确认问题记录原文、位置、触发步骤及具体修改建议。

按语义判断，避免误判“应急演练”“模拟考试”“数据接口管理”等正常业务内容。源码注释和内部变量名不作为界面文案问题。修复文案不能掩盖功能缺陷，也不能将尚未发生的操作改写为成功。

## 使用前准备

需要支持技能指令的 AI 编码助手，以及可实际操作浏览器或电脑的工具。Codex 环境可使用 `mcp__cua_repl`；其他环境需提供等效能力。仓库本身不包含自动化浏览器运行器，不是执行一条命令即可完成的扫描程序。

建议提供：

1. 原型 HTML 文件、目录或入口 URL，并指出需要检查的版本。
2. 检查范围、核心任务、角色及演示数据；有指定桌面尺寸时一并说明。
3. 可选的产品背景、PRD、功能清单、业务流程和设计规范。

没有需求资料时，可以检查通用交互和流程自洽性，但无法确认全部业务需求是否满足。浏览器操作工具不可用时，只能交付标明限制的静态预检，不能宣称完成交互验收。

## 安装与调用

将仓库下载到本地，保留 `SKILL.md`、`agents/`、`references/`、`assets/` 之间的相对目录关系。

在使用默认技能目录的 Codex 环境中，可将仓库克隆到 `~/.codex/skills/html-prototype-audit`；如果配置了 `CODEX_HOME`，则使用对应的 `skills/html-prototype-audit` 目录。目标目录已存在时，先检查内容，不要直接覆盖。

```bash
git clone https://github.com/IMinnn/-Html-Prototype-Audit-Skill.git \
  ~/.codex/skills/html-prototype-audit
```

也可以保存在项目目录中，向 AI 明确提供 `SKILL.md` 的路径，要求读取并按其流程执行。

示例请求：

```text
使用 $html-prototype-audit 检查指定目录中的 HTML 原型。
实际遍历各页面、菜单和交互，重点检查业务闭环、列表分页、附件操作及演示性质文案。
只检查，不修改原型，输出检查报告和可直接交给 AI 修改的问题清单。
```

结合需求检查：

```text
使用 $html-prototype-audit，结合提供的 PRD 和业务流程检查 HTML 原型。
建立需求覆盖映射，区分已确认问题、待确认规则及未验证场景。
每个问题写明页面、模块、按钮、复现步骤、修改建议及验收标准。
```

复测请求：

```text
使用 $html-prototype-audit 按上次问题清单复测已修改的原型。
保留原问题 ID，实际验证验收条件，并检查共享组件和关联页面。
```

## 输出内容

默认输出以下文件：

```text
检查报告.md
问题清单.json
evidence/          # 仅在需要截图证据时生成
```

Markdown 报告包含检查边界、覆盖记录、问题索引和明细、修复顺序、待确认项及体验建议；有需求资料时增加需求覆盖映射。JSON 用于 AI 读取和后续追踪，两种输出中的问题 ID、状态和统计应一致。

每个确认问题应说明：

- 哪个页面、模块、控件有问题，以及如何进入。
- 前置条件、测试数据、复现步骤、实际结果和预期结果。
- 判断依据、影响范围、优先级及证据。
- 具体修改建议、可执行的验收步骤和可复制的 AI 修改指令。

结果区分“通过、问题、待确认、未验证、不适用”。问题按 P0–P3 分级；业务规则不明时列为待确认，不虚构需求或结论。

例如，分页问题不能只写“完善分页”，应明确“删除末页唯一记录后页码越界”，并要求验证删除后总数、当前页和显示记录是否同步更新。

## 执行边界

- 默认只检查并生成报告，修复原型需要用户明确要求。
- 实际操作用于隔离的本地原型或明确的演示数据；发现连接真实业务服务时，停止相关写操作并确认测试范围。
- 不把弹出“成功”提示当作操作完成的证明；需核对列表、详情、状态或文件结果。
- 不用源码阅读代替页面实测，不用少数页面抽样冒充全量检查。
- 保留交付报告和必要证据，清理临时样例、截图草稿和自己启动的临时服务。
